# Lessons learned

Traps found while building Neeko, each verified against Firefox 156.0.1 and
the tools as they are. Read the section for whatever you're about to touch.
Add to it whenever something costs you time.

## Artifact builds (the dev build)

- **The C++/Rust comes prebuilt from Mozilla's official build.**
  - Compile-time gates are Mozilla's, and telemetry uploads are compiled on.
  - `StaticPrefList.yaml` edits do nothing; override prefs in pref files.
  - The binary must stay named `firefox`.
  - Mozilla's core expects Firefox-named GPU and media helper apps.
    `firefox-neeko.js` works around that.
- **The prebuilt launcher ignores the local `application.ini`.** It uses app
  data compiled into itself (`browser/app/nsBrowserApp.cpp`): vendor
  Mozilla, name Firefox, crash reporter on, Mozilla's update URL. So:
  - `Services.appinfo.name` is "Firefox", and the default profile folder is
    `~/Library/Application Support/Firefox/Profiles`, the user's real
    Firefox profiles. Always launch dev builds with their own profile
    (`make`, the test tools). Release builds (`make release`) compile their
    own launcher and don't have this problem.
  - Build flags only help by removing locally built code and programs:
    `--disable-updater` and `--disable-crashreporter` work that way.
  - Startup logs two harmless errors: the prebuilt core still lists
    `UpdateServiceStub.sys.mjs` and `CrashService.sys.mjs`, which those
    flags removed.
  - Dev bundles still contain Mozilla's `crashreporter.app` (artifact
    builds copy it). `mach run` disables it with `MOZ_CRASHREPORTER_DISABLE`,
    but direct launches don't, so the crash handler can still write local
    dumps (nothing is sent). Release builds compile it out.
- **`AppConstants` is built locally, even in artifact builds.** It reflects
  Neeko's configuration (`MOZ_TELEMETRY_REPORTING` false, say) while the
  prebuilt core has telemetry compiled on. To ask the compiled core, use
  `Services.telemetry.isOfficialTelemetry`.
- **The revision to download** is read from `engine/sourcestamp.txt`
  (`configs/common/mozconfig`).
- **`mk_add_options` only sets make variables.** The old
  `MOZ_TELEMETRY_REPORTING=` / `MOZ_DATA_REPORTING=` lines did nothing, and
  Surfer's `MOZ_APPUPDATE_HOST` export is ignored. Privacy step 3 replaced
  them with real `ac_add_options` flags.

## App identity, branding and packaging

- **Where each part of an app's identity comes from** (all generated by
  `tools/app.ts`):
  - Program name, and so the profile folder: `--with-app-basename`.
  - macOS bundle id: `--with-distribution-id` (everything but the last part
    of `appId`) plus `MOZ_MACBUNDLE_ID` in the branding folder's
    `configure.sh` (the last part).
  - Display name: `MOZ_APP_DISPLAYNAME` in `configure.sh`, which also names
    the `.app` bundle, plus `brand.ftl` and `brand.properties`.
  - Versions: `--with-version-file-path` points Firefox at the branding
    folder's `version.txt` (the app version, which Neeko keeps at Firefox's
    version) and `version_display.txt` (the browser's own version, shown
    in About). Firefox's `browser/config/version*.txt` are only the fallback.
- **The vendor can't be set from mozconfig.** `MOZ_APP_VENDOR` is a "project
  flag": only Firefox's own `browser/moz.configure` may set it (to
  "Mozilla"). Changing it needs a patch there. It only affects profile
  paths on Windows and Linux (`Mozilla/<name>`), and the app's name already
  keeps those apart from Firefox's.
- **Keep the app version at Firefox's version.** Add-on update checks,
  Remote Settings filters and website compatibility fixes compare against
  `Services.appinfo.version`. A browser version like `0.1.0` there would
  break add-on updates. The browser's version is the display version.
- **Surfer's own branding step is unusable for Neeko.** Given
  `configs/branding/<name>/`, it writes Zen Browser's URLs (welcome page,
  release notes) into `firefox-branding.js`, which Firefox reads last, so
  they'd win over Neeko's privacy prefs. It also requires about 15 image
  files. Neeko generates the branding folder itself.
- **Surfer's internal mozconfig part comes last** and adds
  `--with-branding=browser/branding/<brand>` and
  `--enable-update-channel=<brand>`, where the brand is set with
  `surfer set brand`. Neeko uses the brand `release`, so the generated folder
  is `engine/browser/branding/release/` and release builds are on the
  `release` channel. (Artifact builds' prebuilt core keeps the `default`
  channel.)
- **Surfer's `${vendor}` template is filled with the name**, not the vendor.
  Neeko's mozconfig doesn't use it.
- **`SURFER_MOZCONFIG_ONLY=1 surfer build`** writes `engine/mozconfig` (and
  Firefox's version files) and exits, so the Makefile runs `mach build`
  itself.
- **`mach package` only includes files `browser/installer/package-manifest.in`
  names.** Default pref files are listed one by one (Neeko's patch adds its
  two), and so are chrome jars: a separate `neeko.jar` would be dropped, so
  Neeko's chrome files and the bundled UI go into Firefox's `browser.jar`.
- **Two chrome registrations for one package: the later one wins.** The dev
  UI folder, registered at runtime from `neeko.ui.path`, replaces the
  bundled `neeko-ui` package. `tools/test_api.py` checks it.
- **The macOS app icon comes from `Assets.car` first.** Firefox's
  `Info.plist` names both `firefox.icns` and `CFBundleIconName` `AppIcon`,
  and current macOS uses the asset catalog. `tools/app.ts` compiles one with
  `xcrun actool`.
- **Full builds need their own build folder,** or they'd reconfigure the
  artifact build's folder. `configs/common/mozconfig` sets
  `MOZ_OBJDIR=@TOPSRCDIR@/obj-release` when `NEEKO_FULL_BUILD` is set.

## Full (release) builds

- **Firefox builds a release version with release-grade optimization by
  default.** For a version like 156.0.1, `--enable-release` is on unless
  turned off, so `DEVELOPER_OPTIONS` is off, and
  `config/makefiles/rust.mk` compiles the final Rust library (`gkrust`)
  with `-Clto` in one codegen unit. That single step needs about 10 GB of
  memory. Turning `--enable-release` off also changes C++ flags, so it
  recompiles everything.
- **An 8 GB, 8-core M1 can't do that step.** The first `make release`
  (2026-09-23) ran one job per core: compiles that take a minute took
  twenty, the Glean crate took four hours, and after six hours `gkrust`
  had used 3 minutes of CPU in an hour at 9.7 GB (9 GB of it compressed).
  Pausing all but the oldest jobs (SIGSTOP/SIGCONT) got everything else
  through; `gkrust` never would have.
- **Skipping Rust LTO without touching Firefox:** a make variable given on
  the command line beats the makefile's own, and GNU make takes
  command-line variables from the `MAKEFLAGS` environment variable, so
  `MAKEFLAGS=" -- cargo_rustc_flags="` drops `-Clto` for the final crate
  only. Its dependencies keep their fingerprints and don't recompile.
  `gkrust` then took 20 seconds and the rest of the build 40 minutes.
  `make release` does this automatically below 16 GB (`RUST_LTO=0`), and
  runs one job per 2 GB. Check `cargo_rustc_flags` still exists in
  `rust.mk` after Firefox updates.
- **Local full builds compile Firefox's tests too** (gtests, about 140
  files). `ac_add_options --disable-tests` in the full-build branch of
  `configs/common/mozconfig` would skip them; not tried yet.
- **A release creates `~/Library/Application Support/<name>` and
  `~/Library/Caches/<name>` at startup,** even with `-profile`. The test
  tools remove them afterwards if they were new and are still empty
  (`LeaveNoTrace` in `tools/builds.py`).

## Surfer quirks

- It needs `src/` to exist.
- It creates an empty `tests/` folder.
- On every `surfer build` it writes the brand's `displayVersion` into
  Firefox's `browser/config/version.txt` and `version_display.txt`.
  `tools/app.ts` sets that to Firefox's own version, so nothing changes.
  Never use versions ending in `a1` or `b1` there: artifact builds would
  then look for nightly or beta binaries.
- After exporting a patch (`bun run surfer export <path>`), run
  `bun run surfer import`. That checks the patch applies cleanly and updates
  Surfer's patch count.
- `surfer download` reuses `.surfer/engine/firefox-<version>.source.tar.xz`
  if it's there.

## Hide and plug

- **Chrome frames never deliver `load` to the embedding window.**
  `NeekoWindow` hooks the UI document through the `document-element-inserted`
  observer, then waits for that document's own `DOMContentLoaded`.
- **`frameElement.ownerGlobal` is undefined in module code.** Use
  `ownerDocument.defaultView`.
- **`#browser` is `position: relative`**, so the UI frame needs `z-index: 1`
  and the page area `z-index: 2`.
- **The CSP of `browser.xhtml` only allows `chrome:` frames.** That's why the
  UI is served as `chrome://neeko-ui/`: bundled in `browser.jar`, or
  registered at runtime from the `neeko.ui.path` pref.
- **macOS window buttons** render wherever an element with
  `-moz-default-appearance: -moz-window-button-box` sits. Neeko exposes that as
  `[data-neeko-window-buttons]`.
- **Hit-testing checks out:** the UI background gets UI clicks, and the slot
  gets the remote page.
- **Measured with 300 tabs:** same memory and tab-switch time as stock Firefox,
  and faster to open tabs.
- **What happens to Firefox UI that anchors on hidden toolbars**
  (checked 2026-09-23): permission prompts still open, but pinned to the
  window's top-left corner because their anchor icon is hidden. Downloads
  finish silently: the downloads panel anchors on the hidden toolbar button
  and never opens. Both are on the roadmap.
- **Web page fullscreen** sets `inDOMFullscreen` on the window's root and
  makes the window fullscreen, but Firefox's own layout is what makes the
  page fill it. Neeko's page area keeps the inline position and size
  `NeekoWindow` gives it, so it stayed in the UI's slot with the UI around
  it. `neeko.css` overrides both with `!important` while the attribute is
  there.

## Neeko API

- **`loadSubScript` returns the script's value only when asked.** Use
  `loadSubScriptWithOptions(url, { target, wantReturnValue: true })`.
  `neeko-api.js` evaluates to its install function, so it adds nothing else
  to the UI page's globals.
- **`gBrowser` appears at the browser window's `DOMContentLoaded`**
  (`Tabbrowser.create`). The UI page has always started after that (checked
  at startup and for new windows), but `connectAPI` still handles it
  starting first: the UI's calls wait in the unstarted `MessagePort`.
- **Sleeping tabs wake on most browser properties.** On a lazy tab (no
  `tab.linkedPanel`), reading `canGoBack` or `canGoForward` inserts the
  browser and loads the page. `currentURI` and `contentTitle` are safe.
- **Where the tab signals come from:** `TabAttrModified` with `label` or
  `busy` for title and loading; a tabs progress listener's
  `onLocationChange` for URL and back/forward; `TabBrowserInserted` and
  `TabBrowserDiscarded` for tabs waking and sleeping.
- **Events caused by a call arrive before its reply**, because they share one
  ordered port. Events from anything else (links, shortcuts) arrive a moment
  after the fact, so tests must wait for them.
- **Firefox's wish to focus its address bar is readable.** New tabs opened
  on the New Tab page get `gURLBar.getBrowserState(browser).urlbarFocused`
  set at `addTab`, and Firefox focuses the address bar when they're
  selected. Neeko turns that into the `addressbar` event at `TabSelect`.
- **Cmd+L is a command event** on `#Browser:OpenLocation`, handled by a
  listener on its parent `#mainCommandSet`. A listener on the command itself
  runs first and can `stopPropagation()`. Keys reach it even when focus is
  in the page or the UI frame.
- **Firefox's keyboard shortcuts keep working** (Cmd+T, Cmd+W, Ctrl+Tab,
  Cmd+[, Cmd+], Cmd+R). Before the Cmd+L fallback, Cmd+L logged a harmless
  `getBoxQuads` error from the hidden address bar measuring itself.

## Testing and debugging

- **API test:** `python3 tools/test_api.py` (after `make build`) launches the
  dev build with a fresh profile, a free Marionette port and a bare UI of
  its own, serves test pages from localhost, and runs `tools/test_api.js` in
  the browser window. Then it launches once more with no UI folder, to check
  the bundled UI.
- **Driving the UI like a user needs care with Marionette.** Starting a
  Marionette session, and its own pointer and key actions, move focus into
  the web page. For UI tests, use one session, click with
  `window.synthesizeMouseEvent`, and type with `nsITextInputProcessor`
  (`beginInputTransactionForTests(window)`, then `keydown`/`keyup`), which
  goes to whatever really has focus. Hover-only controls need a `mousemove`
  first.
- **Much of Firefox only works in the active window.** Keyboard focus,
  permission prompts, the downloads panel opening by itself, and web page
  fullscreen (refused otherwise). Under heavy load macOS can take seconds to
  bring a freshly launched app to the front; the one flaky API test run
  (2026-09-23, right after a long release build) failed two address bar
  focus checks that way. `tools/test_api.js` now waits for its window to be
  active before any check.
- **Marionette:** launch with `-marionette -remote-allow-system-access` and use
  `tools/marionette.py` to run JavaScript in the browser window or synthesize
  clicks.
- **Screenshots:** `screencapture -x -o -l <window id>`, with the window id
  from `CGWindowListCopyWindowInfo` (the process's on-screen layer-0 window).
  ruri's bridge can't see this app's window.
- **mach hides its output** when it detects an AI agent (`AI_AGENT`,
  `CLAUDECODE` and others). `./mach build --verbose` shows everything.
- **The user has another Firefox build project (`toji`) on this machine.**
  Only ever kill processes under `/neeko/engine/obj-…` (as `make stop` does).
- **The privacy test** (`tools/test_privacy.py`) runs mitmproxy through
  `uvx` (pinned version, nothing installed), trusts its fresh certificate in
  a brand-new profile with NSS's `certutil` (the dev build's, since packaged
  apps don't ship one), and watches `lsof` for connections that skip the
  proxy. With telemetry upload switched back on, some upload went out
  directly, not through the proxy, so that check matters.
- **Quitting normally needs Marionette on macOS.** Firefox doesn't handle
  SIGTERM there, and killing it skips shutdown, when shutdown pings would
  go. The privacy test enables Marionette only to quit and to read
  about:telemetry/about:glean, with `remote.prefs.recommended=false`.
  Chrome-context commands also need `-remote-allow-system-access`.
- **about:glean fills in its upload status late,** and its placeholder says
  "enabled". Wait for its `uploadEnabled: true|false` line before reading
  the status. Its "disabled, but we're lying to the SDK" message means
  upload is actually on.
- **Never run the privacy test through Marionette** (or set
  `remote.prefs.recommended=false`). Marionette applies its own "recommended
  prefs", which turn off telemetry, captive portal checks and more, hiding
  exactly the defaults under test. Reading default values with
  `Services.prefs.getDefaultBranch("")` is fine, since those prefs are user
  values.
- **Firefox Labs and Nimbus:** with studies off, Nimbus still enables its
  recipe loader for Firefox Labs, on a 6-hour timer
  (`app.normandy.run_interval_seconds`) that starts counting at first
  launch. A 4-minute privacy test won't see that request; it goes to the
  kept Remote Settings host and enrolls in nothing unless the user opts in.

## Git

- **Git refuses local-path submodules** unless run with
  `-c protocol.file.allow=always` (`tools/new-browser.ts` does this for local
  Neeko paths).
- **`git describe --tags` picks up feature tags** (`feat-…`). Use
  `--match 'v*'` for release versions.

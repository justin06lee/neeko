# Lessons learned

Traps found while building Neeko, each verified against Firefox 156.0.1 and
the tools as they are. Read the section for whatever you're about to touch.
Add to it whenever something costs you time.

## Artifact builds (the dev build)

- **The C++/Rust comes prebuilt from Mozilla's official build.**
  - Compile-time gates are Mozilla's, and telemetry uploads are compiled on.
  - `StaticPrefList.yaml` edits do nothing; override prefs in pref files.
  - The binary must stay named `firefox`.
  - Mozilla's core expects Firefox-named GPU and media helper apps.
    `firefox-neeko.js` works around that.
- **The prebuilt launcher ignores the local `application.ini`.** It uses app
  data compiled into itself (`browser/app/nsBrowserApp.cpp`): vendor
  Mozilla, name Firefox, crash reporter on, Mozilla's update URL. So:
  - `Services.appinfo.name` is "Firefox", and the default profile folder is
    `~/Library/Application Support/Firefox/Profiles`, the user's real
    Firefox profiles. Always launch dev builds with their own profile
    (`make`, the test tools). Release builds (`make release`) compile their
    own launcher and don't have this problem.
  - Build flags only help by removing locally built code and programs:
    `--disable-updater` and `--disable-crashreporter` work that way.
  - Startup logs two harmless errors: the prebuilt core still lists
    `UpdateServiceStub.sys.mjs` and `CrashService.sys.mjs`, which those
    flags removed.
  - Dev bundles still contain Mozilla's `crashreporter.app` (artifact
    builds copy it). `mach run` disables it with `MOZ_CRASHREPORTER_DISABLE`,
    but direct launches don't, so the crash handler can still write local
    dumps (nothing is sent). Release builds compile it out.
- **`AppConstants` is built locally, even in artifact builds.** It reflects
  Neeko's configuration (`MOZ_TELEMETRY_REPORTING` false, say) while the
  prebuilt core has telemetry compiled on. To ask the compiled core, use
  `Services.telemetry.isOfficialTelemetry`.
- **The revision to download** is read from `engine/sourcestamp.txt`
  (`configs/common/mozconfig`).
- **`mk_add_options` only sets make variables.** The old
  `MOZ_TELEMETRY_REPORTING=` / `MOZ_DATA_REPORTING=` lines did nothing, and
  Surfer's `MOZ_APPUPDATE_HOST` export is ignored. Privacy step 3 replaced
  them with real `ac_add_options` flags.

## App identity, branding and packaging

- **Where each part of an app's identity comes from** (all generated by
  `tools/app.ts`):
  - Program name, and so the profile folder: `--with-app-basename`.
  - macOS bundle id: `--with-distribution-id` (everything but the last part
    of `appId`) plus `MOZ_MACBUNDLE_ID` in the branding folder's
    `configure.sh` (the last part).
  - Display name: `MOZ_APP_DISPLAYNAME` in `configure.sh`, which also names
    the `.app` bundle, plus `brand.ftl` and `brand.properties`.
  - Versions: `--with-version-file-path` points Firefox at the branding
    folder's `version.txt` (the app version, which Neeko keeps at Firefox's
    version) and `version_display.txt` (the browser's own version, shown
    in About). Firefox's `browser/config/version*.txt` are only the fallback.
- **The vendor can't be set from mozconfig.** `MOZ_APP_VENDOR` is a "project
  flag": only Firefox's own `browser/moz.configure` may set it (to
  "Mozilla"). Changing it needs a patch there. It only affects profile
  paths on Windows and Linux (`Mozilla/<name>`), and the app's name already
  keeps those apart from Firefox's.
- **Keep the app version at Firefox's version.** Add-on update checks,
  Remote Settings filters and website compatibility fixes compare against
  `Services.appinfo.version`. A browser version like `0.1.0` there would
  break add-on updates. The browser's version is the display version.
- **Surfer's own branding step is unusable for Neeko.** Given
  `configs/branding/<name>/`, it writes Zen Browser's URLs (welcome page,
  release notes) into `firefox-branding.js`, which Firefox reads last, so
  they'd win over Neeko's privacy prefs. It also requires about 15 image
  files. Neeko generates the branding folder itself.
- **Surfer's internal mozconfig part comes last** and adds
  `--with-branding=browser/branding/<brand>` and
  `--enable-update-channel=<brand>`, where the brand is set with
  `surfer set brand`. Neeko uses the brand `release`, so the generated folder
  is `engine/browser/branding/release/` and release builds are on the
  `release` channel. (Artifact builds' prebuilt core keeps the `default`
  channel.)
- **Surfer's `${vendor}` template is filled with the name**, not the vendor.
  Neeko's mozconfig doesn't use it.
- **`SURFER_MOZCONFIG_ONLY=1 surfer build`** writes `engine/mozconfig` (and
  Firefox's version files) and exits, so the Makefile runs `mach build`
  itself.
- **`mach package` only includes files `browser/installer/package-manifest.in`
  names.** Default pref files are listed one by one (Neeko's patch adds its
  two), and so are chrome jars: a separate `neeko.jar` would be dropped, so
  Neeko's chrome files and the bundled UI go into Firefox's `browser.jar`.
- **Two chrome registrations for one package: the later one wins.** The dev
  UI folder, registered at runtime from `neeko.ui.path`, replaces the
  bundled `neeko-ui` package. `tools/test_api.py` checks it.
- **The macOS app icon comes from `Assets.car` first.** Firefox's
  `Info.plist` names both `firefox.icns` and `CFBundleIconName` `AppIcon`,
  and current macOS uses the asset catalog. `tools/app.ts` compiles one with
  `xcrun actool`.
- **mach makes the dev `.app` afresh on every build.** The tools tier
  (`assemble_macos_bundle`) deletes the bundle and copies `dist/bin` back
  in, so anything put in it by hand is gone after the next `mach build`, and
  files put in `dist/bin` land in `Contents/Resources`, not
  `Contents/MacOS`. `make build` links the app's helpers in after mach
  (`tools/app.ts helpers`).
- **`mach package`'s disk image holds its own copy of the app.** Files added
  to the packaged `.app` afterwards (an app's helpers) need the disk image
  made again: `tools/app.ts` (makeDiskImage) follows mozpack's `dmg.py`
  with `hdiutil`, since Mozilla's `make_dmg` action needs the build's
  config and may fetch toolchains.
- **codesign takes no comments in an entitlements file:** "Failed to parse
  entitlements: AMFIUnserializeXML: syntax error". Explain them elsewhere.
- **Full builds need their own build folder,** or they'd reconfigure the
  artifact build's folder. `configs/common/mozconfig` sets
  `MOZ_OBJDIR=@TOPSRCDIR@/obj-release` when `NEEKO_FULL_BUILD` is set.

## Full (release) builds

- **Firefox builds a release version with release-grade optimization by
  default.** For a version like 156.0.1, `--enable-release` is on unless
  turned off, so `DEVELOPER_OPTIONS` is off, and
  `config/makefiles/rust.mk` compiles the final Rust library (`gkrust`)
  with `-Clto` in one codegen unit. That single step needs about 10 GB of
  memory. Turning `--enable-release` off also changes C++ flags, so it
  recompiles everything.
- **An 8 GB, 8-core M1 can't do that step.** The first `make release`
  (2026-09-23) ran one job per core: compiles that take a minute took
  twenty, the Glean crate took four hours, and after six hours `gkrust`
  had used 3 minutes of CPU in an hour at 9.7 GB (9 GB of it compressed).
  Pausing all but the oldest jobs (SIGSTOP/SIGCONT) got everything else
  through; `gkrust` never would have.
- **Skipping Rust LTO without touching Firefox:** a make variable given on
  the command line beats the makefile's own, and GNU make takes
  command-line variables from the `MAKEFLAGS` environment variable, so
  `MAKEFLAGS=" -- cargo_rustc_flags="` drops `-Clto` for the final crate
  only. Its dependencies keep their fingerprints and don't recompile.
  `gkrust` then took 20 seconds and the rest of the build 40 minutes.
  `make release` does this automatically below 16 GB (`RUST_LTO=0`), and
  runs one job per 2 GB. Check `cargo_rustc_flags` still exists in
  `rust.mk` after Firefox updates.
- **Local full builds compile Firefox's tests too** (gtests, about 140
  files). `ac_add_options --disable-tests` in the full-build branch of
  `configs/common/mozconfig` would skip them; not tried yet.
- **A new app version recompiles all of Firefox's C/C++,** unless
  `make release` steps in. Configure writes every value it found into the
  build folder's `config/autoconf.mk`, the app's version
  (`MOZ_APP_VERSION_DISPLAY`) and the shell's whole `PATH` among them, and
  every C/C++ object depends on that file (`config/rules.mk`,
  `$(OBJS): $(GLOBAL_DEPS)`). Surfer rewrites `browser/config/version*.txt`
  on every build, so configure always runs again. On the 8 GB M1 that was
  about 3 hours for a version bump. `make release` now runs `mach configure`
  first, and where only those two lines changed, gives `autoconf.mk` its old
  time back: the version reaches compiled code only through its folders'
  `backend.mk` (Glean's `FOG.cpp`, `tools/performance`, AppConstants), which
  rebuild them anyway, and `tools/test_release.py` checks it in About.
  `config.statusd/substs/` (one file per value, rewritten only when it
  changes) shows which values a configure changed.
- **A release creates `~/Library/Application Support/<name>` and
  `~/Library/Caches/<name>` at startup,** even with `-profile`. The test
  tools remove them afterwards if they were new and are still empty
  (`LeaveNoTrace` in `tools/builds.py`).

## Linux

- **Linux's content sandbox reads extra folders from one pref,**
  `security.sandbox.content.read_path_whitelist`: a comma-separated list,
  folders ending in `/` (without it a path is one file). macOS's are
  `security.sandbox.content.mac.testing_read_path1` and `2`. `mach run`
  lets content read `engine/` (`MOZ_DEVELOPER_REPO_DIR`), but Neeko's `src/`
  and an app's `pages/` are outside it (`make run`,
  `tools/builds.py`'s `sandbox_reads`).
- **The prebuilt program is Firefox, and on Linux Firefox's folder is the
  user's real Firefox's:** `~/.config/mozilla/firefox` (or
  `~/.mozilla/firefox`). Even with its own `-profile`, every launch makes
  `Crash Reports/` (with `events/` and an empty `crash_helper_server.log`)
  and `Pending Pings/` there: the crash reporter sets those folders up
  whenever the compiled app data turns it on, and `MOZ_CRASHREPORTER_DISABLE`
  only stops the handler and the crash helper, not the folders. They're
  empty, and a Firefox makes them itself; macOS dev builds do the same in
  `~/Library/Application Support/Firefox`. The test tools launch Linux dev
  builds with `MOZ_CRASHREPORTER_DISABLE`, as `mach run` does.
- **`-app <application.ini>` runs the prebuilt program as another app**
  (`browser/app/nsBrowserApp.cpp`). It must be the first argument, and the
  file's folder becomes the app folder, so the file goes in `browser/`,
  next to the app's `omni.ja`. The build writes one (`dist/bin/application.ini`,
  unused otherwise) with the app's name and no `[Crash Reporter]` section,
  since Neeko's builds leave the crash reporter out. With it the profiles
  are in the app's own folder and no crash reporter starts at all. Firefox
  clears `XUL_APP_FILE` once it has started (keeping it for its own
  restarts), so programs it opens don't inherit it. `make install`'s
  launcher uses it.
- **`RemotingName` is the app's name to the desktop:** Firefox's program
  name for GTK (`g_set_prgname`, and the X11 class GDK makes from it), its
  D-Bus service (`org.mozilla.<name>.<profile>`), the `desktop-entry` of its
  notifications (unless `MOZ_DESKTOP_FILE_NAME` says otherwise) and of its
  media controls. The build's is `firefox`. `--class` sets the X11 class
  exactly; GTK takes it (and `--name`) off the command line before Firefox
  forwards a command line to a running copy. A browser window's X11 name is
  `Navigator`, from its `windowtype`.
- **A second launch with the same profile joins the running one** (the
  command line goes over D-Bus, keyed by the profile's path), so launching
  an installed browser again opens a window in it, and different profiles
  never meet: an installed browser never talks to the user's Firefox.
- **The default browser, on GNOME** (`nsGNOMEShellService`): the browser is
  the default while the http handler's program is `MOZ_APP_LAUNCHER` (or
  else its own binary), and `setDefaultBrowser` picks the desktop entry
  whose `Exec` program is that. Firefox unsets `MOZ_APP_LAUNCHER` for the
  programs it opens. So an installed browser's launcher sets it to itself,
  and its desktop entry runs the launcher.
- **On GNOME, Firefox draws its own titlebar** (`browser.tabs.inTitlebar`'s
  default, 2): no system frame (`_MOTIF_WM_HINTS` decorations 0), and its
  window buttons in the tab strip, which Neeko hides, so the window had
  none. `firefox-neeko.js` (preprocessed) sets 0 with GTK: the system's
  titlebar.
- **Artifact builds package fine** (`mach package`), but compressing the
  archive took five minutes on a small arm64 machine, and installing only
  needs the program's folder: `mach build browser/installer/stage-package`
  makes `dist/firefox` alone, in seconds once it has been made. mach tells
  the desktop when a long step ends; `MOZ_NOSPAM=1` stops it. Staging warns
  that `libonnxruntime.so` is missing: the artifacts don't have Firefox's
  local AI runtime.
- **Linux window managers place new windows themselves,** and size their
  frames their own way, so `window.open`'s `left`, `top`, `outerWidth` and
  `outerHeight` don't stick; `moveTo` and `resizeTo` once the window is
  shown do (`replaceWindow`). (Wayland lets no program place windows.)
- **The build's `certutil` needs the build's NSS** on Linux:
  `LD_LIBRARY_PATH` at its folder, or it finds the system's older one
  (`NSS_3.117 not found`). macOS finds it next to the program.
- **A profile keeps running cached code until the build id changes.**
  Firefox keeps chrome code in each profile's startup cache
  (`~/.cache/mozilla/<name>/<profile>/startupCache`) and only drops it when
  `compatibility.ini`'s `LastVersion` (version, app build id, platform build
  id) no longer matches, or with `-purgecaches` (which `mach run` passes).
  An artifact build's app build id only changes when the build is
  configured again, so an install over an old one ran the old Neeko code in
  every existing profile. The installer stamps each install's
  `application.ini` with its own build id (the install time). Firefox only
  compares major versions to spot a downgrade, so build ids can't trigger
  its "older version" protection. `.purgecaches` in the app folder isn't
  enough: Firefox deletes it at the first profile's launch.
- **Declaring web types can make a browser the default by itself.** With no
  default in any `mimeapps.list` (a fresh Ubuntu user has none), GIO and
  `xdg-mime` take the first app that declares the type, and the user's own
  `~/.local/share/applications` comes first. So installing a desktop entry
  with `MimeType=x-scheme-handler/http;...` moved every link to the new
  browser. The installer checks each type with `gio mime` before and after,
  and where it moved, sets the old app with `gio mime <type> <app>`
  (`tools/test_install.py`). `LC_ALL=C` keeps `gio`'s output parseable.
- **Other browsers' data is under the home folder** on Linux
  (`ChromeMigrationUtils`: `Home/.config/google-chrome` and so on), not
  `ULibDir`, so the import test's fake stands in for `Home` there.

## Surfer quirks

- It needs `src/` to exist.
- It creates an empty `tests/` folder.
- On every `surfer build` it writes the brand's `displayVersion` into
  Firefox's `browser/config/version.txt` and `version_display.txt`.
  `tools/app.ts` sets that to Firefox's own version, so nothing changes.
  Never use versions ending in `a1` or `b1` there: artifact builds would
  then look for nightly or beta binaries.
- After exporting a patch (`bun run surfer export <path>`), run
  `bun run surfer import`. That checks the patch applies cleanly and updates
  Surfer's patch count.
- `surfer download` reuses `.surfer/engine/firefox-<version>.source.tar.xz`
  if it's there.

## Hide and plug

- **Chrome frames never deliver `load` to the embedding window.**
  `NeekoWindow` hooks the UI document through the `document-element-inserted`
  observer, then waits for that document's own `DOMContentLoaded`.
- **`frameElement.ownerGlobal` is undefined in module code.** Use
  `ownerDocument.defaultView`.
- **`#browser` is `position: relative`**, so the UI frame needs `z-index: 1`
  and the page area `z-index: 2`.
- **The CSP of `browser.xhtml` only allows `chrome:` frames.** That's why the
  UI is served as `chrome://neeko-ui/`: bundled in `browser.jar`, or
  registered at runtime from the `neeko.ui.path` pref.
- **macOS window buttons** render wherever an element with
  `-moz-default-appearance: -moz-window-button-box` sits. Neeko exposes that as
  `[data-neeko-window-buttons]`.
- **`-moz-window-dragging` only counts in a window's top chrome document.**
  `nsDocShell::GetWindowDraggingAllowed` is true for a top-level chrome
  docshell and false for frames, so the display list drops the UI frame's
  drag areas (`nsDisplayListBuilder::AdjustWindowDraggingRegion`) and the
  window couldn't be dragged at all. The scriptable
  `docShell.windowDraggingAllowed = true` on the UI's docshell lets them
  through (NeekoWindow sets it for every UI document). Double-click to zoom
  or minimize then comes free: the macOS widget does it on a second mouseup
  in the drag region (`AppleActionOnDoubleClick`).
- **Changing only `-moz-window-dragging` doesn't redo the drag region.** Its
  style change is just `nsChangeHint_SchedulePaint`, and retained display
  lists keep the frame's old area until the frame is rebuilt (shown, moved,
  restyled otherwise). Elements added or shown with it count at once.
- **The drag region ignores what's on top.** A UI marking its whole
  background `drag` would make the page above it drag the window too, so
  neeko.css makes the page area `no-drag`.
- **Reading the drag region in a test:** on macOS, nsCocoaWindow covers
  everything that isn't draggable with `NonDraggableView`s inside
  `[[window mainChildView] nonDraggableViewsContainer]`; their `hitTest:`
  returns nil, so hit-testing can't tell. `tools/test_api.js` reads their
  frames through ctypes and libobjc (`macWindowDragging`).
- **Hit-testing checks out:** the UI background gets UI clicks, and the slot
  gets the remote page.
- **An iframe takes the pointer over its whole box,** transparent or not
  (`nsSubDocumentFrame` adds its own event-receiving background item), so a
  UI raised above the page can't let clicks through where it's
  transparent. Only `pointer-events: none` on the frame does, for all of it.
  So for `data-neeko-overlay`, NeekoWindow raises the UI frame (z-index 4,
  above the notification bars' 3)
  and gives it a `clip-path`: the whole window, minus the page (a path with
  its rounded corners, wound the other way), plus each overlay's box and
  shadow. `clip-path` clips hit-testing as well as painting, and the wheel
  still scrolls the page through the clipped-out part (checked 2026-09-25).
- **A blurred shadow reaches about 1.41 times its blur radius** past the
  shadow's edge: `nsContextBoxBlur::GetBlurRadiusMargin` uses a standard
  deviation of half the blur radius, times `GAUSSIAN_SCALE_FACTOR` (2.82).
  Clipping at the blur radius left a hard edge; NeekoWindow allows 1.5
  times.
- **The UI frame is transparent** where the UI page paints nothing (no
  opaque canvas, even with `color-scheme: dark`), so the page shows through
  an overlay's shadow if the UI paints no background under its slot.
- **Testing what's drawn, remote page included:**
  `browsingContext.currentWindowGlobal.drawSnapshot(rect, 1, "white")` in
  the browser window gives an `ImageBitmap` of the window as composited.
- **Measured with 300 tabs:** same memory and tab-switch time as stock Firefox,
  and faster to open tabs.
- **Fullscreen has two signals.** `MozDOMFullscreen:Entered` and
  `:Exited` on the browser window for web page fullscreen (the chrome
  document's `fullscreenElement` is the page's `<browser>` meanwhile), and
  `fullscreen` for the window itself, fired once `window.fullScreen` has
  changed. A page going fullscreen fires both.
- **Window fullscreen on macOS is native**: setting `window.fullScreen`
  moves the window to its own Space with the system animation, even though
  page fullscreen isn't (`full-screen-api.macos-native-full-screen` is
  false). The API test does it once; expect the screen to switch.
- **Firefox's panels hang from toolbar icons, which Neeko hides** (checked
  2026-09-23):
  - `PopupNotifications` (permission prompts, password saving, add-on
    installs) looks for a visible anchor, finds none and opens
    `#notification-popup` with no anchor: the window's top-left corner.
  - `ConfirmationHint`, the menu button's notices and the bookmark panel open
    against their hidden icon. The "add-on added" notice didn't appear at
    all.
  - `NeekoPanels` moves them to an anchor along the top of the page:
    `panel.moveToAnchor()` in a capturing `popupshowing` listener works,
    because the popup is "showing" and not positioned yet.
  - The anchor follows the page by CSS anchor positioning (`anchor-name` on
    `#tabbrowser-tabbox`), which Firefox 156 has on without a pref. The
    anchored element must come after the page area in the document. Open
    panels follow it when the UI moves the page.
  - A panel lines up on the right if its hidden anchor is after the address
    bar in `#nav-bar` (a toolbar button), otherwise on the left.
  - The downloads panel never even opens: `DownloadsButton.getAnchor()`
    returns null when the button's toolbar is hidden
    (`downloads/content/indicator.js`). `NeekoPanels` wraps it to return
    the page's anchor. `DownloadsButton` is a lazy global
    (`XPCOMUtils.defineLazyScriptGetter`), so Neeko hooks the getter rather
    than creating the object early.
  - After a download has opened the panel, Firefox only animates the
    toolbar button for later ones while another is running
    (`DownloadsCommon.sys.mjs`, `_notifyDownloadEvent`), which a hidden
    button doesn't show.
  - After Firefox updates, check `#notification-popup` is still
    `PopupNotifications`' panel (`browser.js`); `tools/test_api.js` checks
    a real location prompt.
- **Firefox's notification bars live in its toolbox** (Firefox 156): the
  global ones and each tab's (a blocked pop-up, a slow page) are in
  `#notifications-toolbar`, the tabs' in its `#tab-notification-deck`
  (`Tabbrowser.getNotificationBox`). Hiding the whole toolbox hid them, so
  until v0.11.0 nobody under Neeko ever saw a blocked pop-up. `neeko.css`
  now hides the toolbox's other children and shows it over the top of the
  page, with `--neeko-page-*` from `NeekoWindow` (CSS anchor positioning
  can't: the toolbox comes before the page in the document), and a
  ResizeObserver pads the page down by the bars' height. Bars added while a
  page is still loading vanish when its address changes (Firefox removes
  them on navigation), which caught out the first version of the test.
- **Firefox pulls tab-modal dialogs 5px up** to overlap its toolbar
  (`content-area.css`, `margin-top: -5px`); the page area's `overflow: clip`
  cut their top edge off, so `neeko.css` hangs them 8px inside the page.
- **Web page fullscreen** sets `inDOMFullscreen` on the window's root and
  makes the window fullscreen, but Firefox's own layout is what makes the
  page fill it. Neeko's page area keeps the inline position and size
  `NeekoWindow` gives it, so it stayed in the UI's slot with the UI around
  it. `neeko.css` overrides both with `!important` while the attribute is
  there.

## Neeko API

- **`loadSubScript` returns the script's value only when asked.** Use
  `loadSubScriptWithOptions(url, { target, wantReturnValue: true })`.
  `neeko-api.js` evaluates to its install function, so it adds nothing else
  to the UI page's globals.
- **`gBrowser` appears at the browser window's `DOMContentLoaded`**
  (`Tabbrowser.create`). The UI page has always started after that (checked
  at startup and for new windows), but `connectAPI` still handles it
  starting first: the UI's calls wait in the unstarted `MessagePort`.
- **Sleeping tabs wake on most browser properties.** On a lazy tab (no
  `tab.linkedPanel`), reading `canGoBack` or `canGoForward` inserts the
  browser and loads the page. `currentURI` and `contentTitle` are safe.
- **Where the tab signals come from:** `TabAttrModified` with `label` or
  `busy` for title and loading; a tabs progress listener's
  `onLocationChange` for URL and back/forward; `TabBrowserInserted` and
  `TabBrowserDiscarded` for tabs waking and sleeping.
- **Back skips pages nobody interacted with.** Firefox's
  `browser.navigation.requireUserInteraction` (on by default) leaves history
  entries without a click, key, scroll or tap in the page out of Back, so
  `canGoBack` is false when every earlier page is untouched (a tab opened on
  one page, then sent to another by `nav.go()`). Neeko reports Firefox's
  answer. An entry's `hasUserInteraction` is writable from chrome code.
- **Permission prompts all pass through `PopupNotifications.show()`**
  (`browser/modules/PermissionUI.sys.mjs`), with a message, a main action,
  secondary actions and options. `NeekoPanels` wraps `show` on the window's
  `PopupNotifications`, a lazy global made on first use.
  - `options.dismissed` doesn't keep Firefox's panel closed: permission
    prompts are `persistent`, which shows them anyway. `options.neverShow`
    does. Clearing it and calling `anchorVisibilityChange()` (public) makes
    Firefox show them again, which is how prompts go back to Firefox when
    the UI stops listening.
  - Answering is what Firefox's button handler does: call the action's
    `callback({ checkboxChecked, source })`, then `notification.remove()`.
    Firefox's checks happen in its button handler, not the callback, so
    Neeko repeats them: the window must be active, and actions without
    `disableSecurityDelay` (only Block has it) wait
    `security.notification_enable_delay` after the prompt appears.
  - Prompts shown `dismissed` from the start are Firefox's "post-prompts",
    requests it already turned down (a site asking for notifications
    without a click) that only get an icon. Neeko doesn't hand those over.
  - Camera, microphone and screen sharing (`WebRTCParent.sys.mjs`) read the
    chosen device from menus inside Firefox's panel, so they can't be
    answered without it.
  - `displayURI` is false for some prompts (location); the site is then only
    `options.name`, the `<>` in the message.
- **Downloads come from `Downloads.getList()`** (`Downloads.PUBLIC`, or
  `PRIVATE` in private windows); a view added with `addView` hears
  `onDownloadAdded` for every download already there first, so Neeko only
  sends `start` for ones added after.
  - Firefox reports progress at most every 400ms
    (`kProgressUpdateIntervalMs`), so the last update before success can
    be behind. Once a download succeeds, `target.size` is the file's size.
  - Firefox opens its downloads panel by itself with `showPanel()` and no
    arguments (`DownloadsCommon.sys.mjs`); the toolbar button passes
    `openedManually`. `NeekoPanels` skips the first kind while the UI shows
    downloads.
  - `DownloadsCommon` is `moz-src:///browser/components/downloads/`, not
    `resource:///modules/`, in Firefox 156.
  - Tests can replace `DownloadIntegration.launchFile` and
    `showContainingDirectory` (Firefox's own tests do) to check "open" and
    "show" without launching an app or Finder.
  - A download that's cut short can look finished. The API test's broken
    download resets the connection (`SO_LINGER` 0) instead, which fails it
    as `becauseSourceFailed`.
  - PDFs open in a Firefox tab when they finish downloading, by default.
- **Events caused by a call arrive before its reply**, because they share one
  ordered port. Events from anything else (links, shortcuts) arrive a moment
  after the fact, so tests must wait for them.
- **Tab icons are mostly `data:` URLs.** The content process loads a page's
  favicon (`FaviconLoader.sys.mjs`), and `LinkHandlerParent` redraws it on a
  canvas at its own size and calls `gBrowser.setIcon()` with the canvas's
  `data:` URL (or an ICO one for several sizes). Only `chrome:`, `about:` and
  `resource:` icons stay ordinary URLs (`TRUSTED_FAVICON_SCHEMES`). The tab's
  `image` attribute holds it, and `TabAttrModified` reports `image`
  changes. Neeko turns each distinct `data:` icon into one `blob:` URL made
  in the UI page (`URL.createObjectURL` in the UI's window), counted per
  tab and revoked when no tab shows it.
- **SVG tab icons arrive wrapped in `moz-remote-image:`** (with
  `browser.tabs.remoteSVGIconDecoding`, on by default): `setIcon` sets the
  tab's `image` to `moz-remote-image://?url=<the SVG data: URL>&width=…`,
  and that protocol draws the SVG in the page's content process and returns
  a PNG, so untrusted SVG is never decoded in the parent
  (`RemoteImageProtocolHandler.cpp`; `FaviconUtils.sys.mjs` says never to
  display the raw data: URL). Neeko must not make a blob: of the SVG
  inside: it loads the moz-remote-image: URL itself (a system-principal
  channel with an image content policy type, as the handler requires) and
  gives the UI a blob: of the PNG. Toji found these as long URLs in v0.3.0.
- **`crashed` changes without `TabAttrModified`.** `ContentCrashHandlers`
  sets the tab's `crashed` attribute once the dead process has shut down,
  and SessionStore and the tab progress listener remove it quietly, so
  `NeekoAPI` watches that attribute with a MutationObserver.
  `SessionStore.reviveCrashedTab(tab)` is what about:tabcrashed's Restore
  This Tab does.
- **Error pages show in `browser.documentURI`**, as
  `about:neterror?e=<code>&u=<url>…` (also `certerror`, `blocked`,
  `httpsonlyerror`, `restricted`; `nsDocShell::DisplayLoadError`), while
  `currentURI` is the address that failed. For remote browsers,
  `BrowserParent::RecvOnLocationChange` updates `documentURI` before the
  tabs progress listeners hear `onLocationChange`.
- **`openLinkIn()` can't place a tab.** Its "tab" branch calls
  `gBrowser.addTab()` without a `tabIndex`. `tabs.open` calls `addTab()`
  itself with what `openLinkIn()` would pass (system principal,
  `allowThirdPartyFixup`, `focusUrlBar` for blank pages unless
  `AboutNewTab.willNotifyUser`), plus the index, then focuses the page as
  `openLinkIn()` does. Opening at the end and moving it after would send the
  UI an `open` at the wrong place and a `move`.
- **`addTab()` opens in the background unless told otherwise**
  (`inBackground` defaults to true); `openTrustedLinkIn()` sets
  `forceForeground`.
- **`SessionStore.duplicateTab(win, tab, 0, true, { tabIndex })`** is
  Firefox's Duplicate Tab (the context menu moves the copy next to the tab
  afterwards). The copy starts on `about:blank` and gets its page and history
  once the original's state is flushed; selecting it at once is fine.
- **`"use strict"` is a syntax error in a function with destructured
  parameters.** `neeko-api.js` takes its second argument whole.
- **One pref makes everything light or dark: `ui.systemUsesDarkTheme`**
  (int, 1 or 0; `nsXPLookAndFeel`). It stands in for the system's setting,
  and changing it restyles every window (`IntPrefChanged`). The browser
  window, the UI page, Firefox's panels, web pages
  (`layout.css.prefers-color-scheme.content-override`, default 2: "auto")
  and Firefox's own pages (about:preferences, in the parent process, too)
  all follow it, because with the default theme they all come down to the
  system's scheme. `LightweightThemeConsumer` writes
  `browser.theme.toolbar-theme` and `content-theme` (2, "system", for the
  default theme) on every theme update, so setting those instead would be
  undone; a theme with a color scheme of its own still wins in its windows.
- **UI settings are prefs of their own type.** A pref keeps its type: to
  store a boolean where a string was, clear the user value first, which
  only works if there's no default of the old type.
- **What the UI reads without waiting** comes with `neeko-api.js`'s install
  call (`facts`), and change events that NeekoAPI always sends keep it
  current. NeekoAPI starts in the same task as the install (gBrowser
  exists by then), so no change falls in between; if it ever starts later,
  `resync()` sends every setting again.
- **Cmd+D did nothing under Neeko** (until v0.6.0). The bookmark panel
  hangs from the address bar's star: `BookmarkingUI.anchor` asks
  `BrowserPageActions.panelAnchorNodeForAction`, which throws "PageActions:
  No anchor node for bookmark" when the star isn't laid out, so
  `StarUI.showEditBookmarkPopup` fails, and since new bookmarks are only
  saved when that panel closes (`StarUI.showForNewBookmarks`), nothing is
  bookmarked either. `NeekoPanels` redefines the `anchor` getter to fall
  back to the page's anchor. Cmd+D is the `Browser:AddBookmarkAs` command,
  handled by `browser-sets.js` further up, like Cmd+L.
- **Bookmarks are Places items with GUIDs** (12 characters, the same across
  sessions). `PlacesUtils.bookmarks.fetch()` throws on a malformed GUID
  ("Invalid value for property 'guid'"), so check `PlacesUtils.isValidGuid`
  first. `promiseBookmarksTree(guid)` reads a folder with everything under
  it, and each bookmark's `iconUri` if Firefox has an icon for the page.
  Tags are bookmarks inside folders under `tagsGuid`; Places events for them
  have `isTagging`, and `fetch({ url })` leaves them out. Removing a folder
  sends `bookmark-removed` for everything in it too, marked
  `isDescendantRemoval`. Places event times are in milliseconds; the tree's
  are in microseconds.
- **`page-icon:<page URL>`** serves the icon Firefox has stored for a page
  (Places' `PageIconProtocolHandler`), or Firefox's default icon if it has
  none, so check for one (`PlacesUtils.favicons.getFaviconForPage`) to
  report null. Firefox's own bookmarks toolbar uses these URLs.
- **The API's methods can't touch NeekoAPI's private fields.** `METHODS`
  is outside the class, so `this.#field` there is a syntax error that stops
  NeekoAPI loading at all (and with it every window's UI). Give the class a
  method instead.
- **Tab groups are `<tab-group>` elements** among the tabs
  (`tabgroup.js`), holding their tabs, so `tab.group` is the group.
  - `gBrowser.addTabGroup(tabs, { label, color, insertBefore })` puts the
    group at the end of the tabs unless given `insertBefore`; Firefox's
    own "new group" passes the first tab. `color` defaults to
    `tabGroupMenu.nextUnusedColor`; the colors are
    `customElements.get("tabgroup-menu").COLORS`.
  - `group.ungroupTabs()` ungroups; `gBrowser.removeTabGroup(group)`
    closes its tabs. `gBrowser.ungroupTab(tab)` puts a tab just after its
    group; `moveTabToExistingGroup(tab, group)` at its end.
  - Events: `TabGroupCreate` (once, when the element is first connected,
    before its tabs are added), `TabGroupRemoved` (when its last tab
    leaves, from a MutationObserver), `TabGroupUpdate` (label, color),
    `TabGroupCollapse` and `TabGroupExpand`. `TabGrouped` and
    `TabUngrouped` are dispatched on the group, with the tab as `detail`,
    because a tab moving to another window is detached by then. All bubble
    to `tabContainer`.
  - The tab strip's `insertBefore(tab, node)` is `node.before(tab)`, so
    `moveTabTo` to a position among a group's tabs puts the tab in the
    group, as dragging does.
- **The theme goes where Firefox's own values do.** Design tokens set on
  an element from the document win over a shadow root's `:host` rules for
  them, so `notification-message` (its `--info-bar-*` and `--message-bar-*`)
  and the dialog's buttons (on `<dialog>`, read inside its shadow root) take
  the theme from outside. Some Firefox rules set a token with an id
  (`#PopupAutoComplete { --panel-border-radius: var(--popup-border-radius) }`),
  which outranks Neeko's: set the token it reads instead. Where Firefox
  styles properties directly (the find bar's and the status bubble's
  colors, the infobar's gradient stripe), Neeko overrides those.
  - `font-family: var(--x)` with `--x` undefined is invalid at computed-value
    time, which for an inherited property means `unset`: inherit, but on a
    root element that's the initial value, a serif font. The theme always
    defines its font (the system's by default).
  - Firefox's dialogs (`commonDialog.xhtml`) are documents of their own in a
    `<browser>` in the window: `NeekoTheme` catches them at
    `document-element-inserted` and loads its sheets there.
- **Firefox's menus show and hide their own items as they open.** The
  context menu is filled in a `popupshowing` listener on the menu itself
  (`browser-context.js`, at DOMContentLoaded), and menu bar menus unhide
  items in theirs (containers, full screen). A listener on the menu added
  earlier runs before them, so `NeekoMenus` listens on the document: at the
  target, all the menu's own listeners run before the event bubbles up.
  Some context menu items appear a moment later (a link to a highlight,
  translations), so it also watches the open menu with a MutationObserver.
  macOS's native menus follow the `hidden` attribute, even while open.
  - The context menu's navigation items are a `<menugroup>` only on some
    platforms; on macOS they're plain items.
  - Extensions' items have ids with `-menuitem-` (`ext-menus.js`), spell
    suggestions the class `spell-suggestion`.
  - A synthesized right-click opens the context menu in tests:
    `synthesizeMouseEvent` `mousedown`, `contextmenu`, `mouseup`, with
    `button: 2`, over the page. macOS's native context menu doesn't block
    the script.
  - Settings... and Cmd+, are a `command` event on `menu_preferences` (or
    `menu_settings`) handled by a listener on `#main-menubar`; the macOS
    app menu dispatches it to that element. `openPreferences()` opens in
    the current tab if it's a New Tab page.
  - With no window open, macOS shows the hidden window's menu bar
    (`hiddenWindowMac.xhtml`), which `NeekoMenus` trims too.
- **Find in page is `browser.finder`** (`FinderParent`, or `Finder` for a
  page in the parent process), per tab: `fastFind`, `findAgain`,
  `highlight`, setters for case, whole word and diacritics. It reports
  through result listeners, which must have every callback
  (`onFindResult`, `onMatchesCountResult`, `onHighlightFinished`,
  `onCurrentSelection`) or it logs an error: the result first, the match
  count after, from every frame. A count at the limit (1000) comes as -1.
  Firefox's find bar also counts in Glean, which Neeko's calls don't.
  - **Highlight all lives in each page's finder** (`FinderChild` makes a
    `Finder` per document), whose highlighter is made on its first search
    or highlight, off (as the `findbar.highlightAll` pref says). A
    `Finder:HighlightAllChange` sent before then is dropped (`Finder`
    only passes it to a highlighter that exists), so highlighting asked
    for before a tab's first search, or before its page changed, did
    nothing (found by Toji). `NeekoAPI.keepHighlighting` has each page's
    finder make its highlighter (highlighting nothing) and turns it on,
    once per page (`currentWindowGlobal`), before the search.
  - The match colors are look-and-feel prefs: `ui.textHighlightBackground`
    (every match) and `ui.textSelectAttentionBackground` (the selected
    one). The API test paints matches red to count them in a snapshot.
  - Cmd+F, Cmd+G, Cmd+Shift+G and Cmd+E are commands (`cmd_find`...)
    handled by a listener on the command set further up, like Cmd+L.
  - Cmd+F pressed in a page can also put the page's `FindBarChild` into
    passing its keys on to the parent's find bar (`inPassThrough`), until
    the find bar says it has the focus (`Findbar:UpdateState` with
    `isOpenAndFocused`). `requestFind` sends that state when the UI takes
    find, as Firefox's find bar would. Typing into a page after Cmd+F and
    Escape worked with and without it in a test with synthesized keys
    (2026-09-26), so it's a safeguard, not a proven fix.
  - / and ' typed in a page open Firefox's find bar through
    `FindBarParent`, which calls the tab's find bar's `_onBrowserKeypress`
    (making the find bar if needed; `TabFindInitialized` fires on the tab).
    `NeekoWindow` wraps that method on each new find bar.
- **The link the pointer is over** reaches the browser window as an
  `OverLink` event (`XULBrowserWindow.setOverLink` dispatches it first,
  with the raw URL, then works out the text it shows: decoded, trimmed,
  bidi controls escaped, in `XULBrowserWindow.overLink`), so Neeko reads
  the text a microtask later. Loading messages come to tabs progress
  listeners (`onStatusChange(browser, ...)`); Firefox only shows them while
  the tab is busy, so Neeko clears them when it stops. The status bubble
  (`#statuspanel`) says what it shows in its `type` attribute (`overLink`,
  `status`), which `neeko.css` uses to hide the kinds the UI shows.
- **A page's stream, fed from its actor, must be fed as the page's own.**
  `neekoPage.helper.fetch` builds the `Response`'s body as a
  `ReadableStream` of the page's, fed from `NeekoPageChild`. Calling its
  controller's `enqueue`, `close` or `error` through Xrays runs them in the
  actor's realm, so a read the page was waiting on resolved with an object
  made there, which the page saw as `{}`: values `undefined`, `done`
  undefined, abort reasons "Permission denied". Calling them through
  `Cu.waiveXrays(controller)` runs them in the page's realm. Reads made
  after the chunk arrived worked either way, which hid it in a quick test.
  An `exportFunction`'d source is fine for `start`; `cloneInto` with
  `cloneFunctions` handed `start` a controller the actor couldn't use.
- **Helpers aren't spawned "disclaimed"** (`Subprocess.call`'s `disclaim`,
  macOS): a disclaimed script helper on an external disk (the dev build
  links to the app's file) waited for permission to read itself, which
  nobody was asked, and never said its port. Not disclaimed, a helper is
  part of the browser to the system's permissions, as an app's helpers
  are.
- **`fetch` in a system module** works for helpers: no CORS for the system
  principal, `credentials: "omit"` and `cache: "no-store"` keep the
  browser's cookies and cache out, and `redirect: "error"` keeps Neeko's
  headers (the token) from following a redirect elsewhere.
- **A new file in `src/` needs `surfer import`** (`make` does it) before
  `mach build` can see it: Surfer links Neeko's files into `engine/` one by
  one, so a new module listed in `moz.build` fails the build as "does not
  exist" until then.
- **`ownerGlobal` is undefined on nodes in module code, documents
  included** (see Hide and plug): `doc.defaultView`. It cost the context
  menu a debugging round (the watcher threw before it was set up).
- **Containers are user contexts Neeko numbers itself** (from 1000, the
  default one 0), not Firefox's `ContextualIdentityService`: Firefox copes
  with a userContextId it doesn't know (no tab indicator, and session
  restore keeps it), and its own containers (1 to 4, and more that
  extensions make) stay apart. Private windows can have one too
  (privateBrowsingId 1 with a userContextId).
  - A window's first tab takes `window.arguments[5]` (Tabbrowser, before
    the per-window `browser-window-domcontentloaded-before-tabbrowser`
    hook's result is used); setting it makes browser-init.js load the first
    page with the full form of the arguments, which needs `[8]`, a
    triggering principal, or nothing loads. `gBrowserInit.uriToLoadPromise`
    is read (and kept) earlier, for the bookmarks toolbar: a window that
    must load nothing replaces it with null.
  - Every tab goes through `gBrowser.addTab` (session restore through
    `addTrustedTab`), so one wrapper keeps a window's tabs in its
    container. Adopting a tab from another window is `adoptTab` and
    `swapBrowsersAndCloseOther`; dropping one asks
    `tabContainer.tabDragAndDrop.getDropEffectForTabDrag`.
  - Session restore creates a window's tabs before it restores its saved
    values (`extData`), between `SSWindowStateBusy` and
    `SSWindowStateReady`: the window's container is decided at Ready.
  - At a launch that doesn't restore the session (Firefox's default),
    SessionStore still restores the first window, with only its pinned and
    closed tabs and its place, not its `extData`, and still sends Busy and
    Ready. So Ready alone doesn't mean tabs came back: the window's own
    blank tab (the default context) would pass for a restored one. Neeko
    decides only for tabs restore brought back: added while restoring, or
    `SessionStore.isTabRestoring` at Ready, which also catches the blank
    tab when tabbrowser reuses it for a restored tab of the same context
    (`createTabsForSessionRestore`). Fresh-profile tests never see this;
    `tools/test_relaunch.js` relaunches one profile.
    `SessionStore.setCustomWindowValue` needs the window to be followed
    (`__SSi`), from the `browser-window-sessionstore-initialized` hook.
  - `Services.clearData.deleteDataFromOriginAttributesPattern({
    userContextId })` wipes a container, private data included.
  - Wiping doesn't touch the closed windows SessionStore keeps to reopen:
    one reopened after its container was removed, or made ephemeral,
    would load its page in the old user context before the picker. Neeko
    forgets them (`getClosedWindowData`, `forgetClosedWindowById`).
    Closed private windows aren't kept at all.
  - SessionStore is `moz-src:///browser/components/sessionstore/`, not
    `resource:///modules/sessionstore/`, in Firefox 156.
- **The app's pages (`about:<name>`) need registering in every process.**
  Pages with `URI_MUST_LOAD_IN_CHILD` load in a content process, which
  resolves the `about:` address itself, so a dynamically registered
  `nsIAboutModule` (`registerFactory` for
  `@mozilla.org/network/protocol/about;1?what=<name>`) must be registered
  there too: `NeekoPages` shares the names with `Services.ppmm.sharedData`
  and loads a process script (`loadProcessScript(url, true)`, so future
  processes get it too).
  - `URI_CAN_LOAD_IN_PRIVILEGEDABOUT_PROCESS` puts them in the
    `privilegedabout` process, which "cannot be disabled"
    (`ProcessIsolation.cpp`). `URI_SAFE_FOR_UNTRUSTED_CONTENT` gives them a
    content principal for their `about:` address; without
    `MAKE_LINKABLE`, web pages can't load them.
  - Such a page still sees a `Components` object (`typeof Components` is
    "object"), but not `ChromeUtils`, which chrome-only code has.
  - `about:` addresses aren't hierarchical: relative URLs in the page don't
    resolve, hence `<base href="chrome://neeko-pages/content/">`.
  - Runtime chrome registrations (`aomStartup.registerChrome`) reach
    content processes (`nsChromeRegistryChrome` sends them), **but only as
    long as the returned handle lives**: an unkept handle is collected and
    the package vanishes, and later loads fail as "file not found".
- **A `crossorigin` stylesheet from `chrome://neeko-pages/` doesn't apply**
  in an app page (found by Toji, 2026-09-25): `link.sheet` exists, but none
  of its rules apply, and the console says nothing. It only works if the
  same file was loaded without `crossorigin` earlier in the session (the
  shared stylesheet cache), which is why a test that loaded the plain page
  first passed. Module scripts with `crossorigin` load fine. Reproduced in
  headless and windowed dev builds with Toji's Vite-built start page.
- **The content sandbox can't read Neeko's files in dev builds.** The app
  bundle's files are symlinks into `engine/`, and Neeko's there are Surfer's
  symlinks to `src/`, outside the repo dir (`engine/`) that non-packaged
  builds let content processes read. Content-process code of Neeko's (the
  pages' process script and actor) failed to load until `make run` and the
  test tools set `security.sandbox.content.mac.testing_read_path1` (Neeko's
  `src/`) and `_path2` (the app's `pages/`), real paths (`/var` is
  `/private/var`). Packaged builds carry everything inside the app. Never
  set these in shipped prefs: they widen every content process's sandbox.
- **A private window's first page is named, not looked up.**
  `BrowserWindowTracker.openWindow` (File > New Private Window) and the
  `-private-window` flag pass `about:privatebrowsing` as the window's first
  argument, whatever the New Tab page is, while `BROWSER_NEW_TAB_URL`
  (Cmd+T) already follows `AboutNewTab.newTabURL` once it's overridden.
  `gBrowserInit.uriToLoadPromise` reads that argument once and keeps the
  value; the bookmarks toolbar asks for it in `onBeforeInitialXULLayout`,
  before the per-window hook runs, so `NeekoPages.initWindow` replaces the
  kept value (or the argument, if nobody read it yet). Nothing has loaded
  by then.
- **A page's click can be checked, and used up, from its actor.** The
  document's `hasValidTransientUserGestureActivation` and
  `consumeTransientUserGestureActivation()` are chrome-only, so
  `NeekoPageChild` checks them before sending a call that needs a click;
  the parent can't see a page's activation itself. In a test,
  `browser.messageManager.loadFrameScript("data:,content.document.notifyUserGestureActivation(); …")`
  gives the page a click from chrome code (synthesized mouse events from
  the parent don't count as one).
- **The default browser, on macOS:** `ShellService.isDefaultBrowser(false,
  false)` compares the bundle id with the `http` handler (cheap);
  `setDefaultBrowser()` asks Launch Services, and macOS then asks the user
  in its own dialog, telling the app nothing. `NeekoPageParent` waits for
  the browser to become the default or for the app to come back to the
  foreground. `ShellService` is a Proxy whose methods can be replaced for a
  test (the API test does, so it never changes the machine's default).
- **Importing is Firefox's `MigrationUtils`** (what its import wizard,
  `MigrationWizardParent`, uses): `availableMigratorKeys` (every importer
  for the platform, installed or not; names are the Fluent strings
  `migration-wizard-migrator-display-name-<key>`), `getMigrator(key)`
  (null if not installed), `getSourceProfiles()` (null for one profile),
  `getMigrateData(profile)` (a bitmask of `resourceTypes`), and
  `migrate(types, false, profile, callback)`, which resolves once every
  type is done, with `getImportedCount("bookmarks" | "logins")` after.
  - Its `EXTENSIONS` type matches extensions on addons.mozilla.org, the
    only part that goes online: Neeko never asks for it.
  - Importers keep what they found (profiles, resources) until
    `MigrationUtils.finishMigration()`.
  - They find other browsers under the `ULibDir` directory, which a test
    can point elsewhere (`Services.dirsvc.undefine`, then `set`), with a
    fake Chrome profile: `Local State` (`profile.info_cache`) and
    `Default/Bookmarks` (`roots.bookmark_bar/other/synced`).
  - Safari's data needs Full Disk Access or the user choosing
    `~/Library/Safari` in a folder picker (`getPermissions(win)`); its
    passwords only come as a file export.
  - A test replaces the native file picker by registering a factory for
    `@mozilla.org/filepicker;1` (and puts the real one back with its CID).
  - `Services.logins.removeLogin` is gone; it's `removeLoginAsync`.
- **The browser window hears the pointer over web pages.** Mouse events
  are dispatched in the parent's document first, with the page's
  `<browser>` as their target, before Firefox forwards them to the content
  process, so a capturing `mousemove` listener on the window follows the
  pointer over the page with nothing running in it (the old Toji used a
  content actor for this). Leaving the window gives a `mouseout` with no
  `relatedTarget`. `window.synthesizeMouseEvent` takes the same path, which
  is how the API test moves the pointer.
- **Don't use `windowUtils.sendNativeMouseEvent` in tests** on this
  machine: it moves the user's real pointer.
- **Firefox's names for platforms** (`AppConstants.platform`) are
  `macosx`, `win` and `linux`; `neeko.platform` says `macos`, `windows`,
  `linux`.
- **Firefox's wish to focus its address bar is readable.** New tabs opened
  on the New Tab page get `gURLBar.getBrowserState(browser).urlbarFocused`
  set at `addTab`, and Firefox focuses the address bar when they're
  selected. Neeko turns that into the `addressbar` event at `TabSelect`.
- **Cmd+L is a command event** on `#Browser:OpenLocation`, handled by a
  listener on its parent `#mainCommandSet`. A listener on the command itself
  runs first and can `stopPropagation()`. Keys reach it even when focus is
  in the page or the UI frame.
- **Firefox's keyboard shortcuts keep working** (Cmd+T, Cmd+W, Ctrl+Tab,
  Cmd+[, Cmd+], Cmd+R). Before the Cmd+L fallback, Cmd+L logged a harmless
  `getBoxQuads` error from the hidden address bar measuring itself.

## Testing and debugging

- **API test:** `python3 tools/test_api.py` (after `make build`) launches the
  dev build with a fresh profile, a free Marionette port and a bare UI of
  its own, serves test pages from localhost, and runs `tools/test_api.js` in
  the browser window. Then it launches once more with no UI folder, to check
  the bundled UI.
- **Driving the UI like a user needs care with Marionette.** Starting a
  Marionette session, and its own pointer and key actions, move focus into
  the web page. For UI tests, use one session, click with
  `window.synthesizeMouseEvent`, and type with `nsITextInputProcessor`
  (`beginInputTransactionForTests(window)`, then `keydown`/`keyup`), which
  goes to whatever really has focus. Hover-only controls need a `mousemove`
  first.
- **Much of Firefox only works in the active window.** Keyboard focus,
  permission prompts, the downloads panel opening by itself, and web page
  fullscreen (refused otherwise). Under heavy load macOS can take seconds to
  bring a freshly launched app to the front, so `tools/test_api.js` waits
  for its window to be active before any check.
- **The flaky `back()` checks** (2026-09-23, under load: about 4 runs in 10
  with 8 busy CPU threads) weren't Neeko's doing. Firefox's Back skips pages
  nobody interacted with (see the Neeko API section), and Page one usually,
  but not always, ended up marked as used by something outside the test. The
  test now marks it itself; 8 runs in 8 passed under the same load.
- **Marionette's recommended prefs change what's under test.** They stop
  the downloads panel opening by itself (`browser.download.alwaysOpenPanel`
  false, `browser.download.panel.shown` true) and turn off the delay before
  a prompt's buttons work (`security.notification_enable_delay` 0). They're
  only applied where the profile has no value of its own, so the API test
  puts Firefox's defaults back in `user.js` (`FIREFOX_PREFS`).
- **The whole API test is one Marionette command,** so its reply comes
  only at the end: 40 seconds on a quiet machine, over 90 under heavy load
  (2026-09-25, load average 40 on 8 cores). `test_api.py` sets the socket's
  timeout to the script's; the old fixed minute failed as a socket
  `TimeoutError`.
- **Timing checks race under load.** "Allow right away is refused" answered
  more than the 500ms delay after the prompt appeared, so Allow went
  through and the next answer found no prompt. The test raises
  `security.notification_enable_delay` for that one check.
- **Crashing a tab on purpose:** kill its content process with
  `nsIProcessToolsService.kill(browser.frameLoader.remoteTab.osPid)` (what
  about:processes does). A SIGKILL leaves no minidump, so there's no crash
  report to offer. Load the page from a site of its own first (the API test
  uses `localhost` next to `127.0.0.1`): Fission gives each site its own
  process, and every tab in the killed process crashes.
- **Making a tab audible in a test:** a page playing a generated tone at
  volume 0.001 is `soundplaying` (Firefox only ignores silence and volume 0),
  but nobody can hear it. It needs `media.autoplay.default` 0 to play
  without a click, and background tabs don't start playing until selected
  (`media.block-autoplay-until-in-foreground`).
- **A connection error without the network:** load `http://127.0.0.1:<a free
  port>/`, which fails as `connectionFailure` at once, instead of an
  unresolvable host, which would still ask the DNS server.
- **Synthesized clicks aren't user activation.** A page that asks for
  notifications on a `window.synthesizeMouseEvent` click gets Firefox's
  "asked without a click" treatment (a dismissed post-prompt).
  `dom.webnotifications.requireuserinteraction` false lifts that for
  testing.
- **`test_api.py`'s test server matches paths exactly,** query string
  included: `/find?again` is a 404. Give each test page its own path.
- **`test_api.js` is one script**, so a `let` it declares twice is a
  syntax error that stops every check; name new variables distinctly.
- **Marionette's `WebDriver:NewSession` takes the capabilities as its bare
  parameters** (geckodriver merges `alwaysMatch` before sending), so
  `{ "unhandledPromptBehavior": "ignore" }`, not wrapped in `capabilities`.
  Without it, any command sent while a page's `alert()` is open dismisses
  it and fails.
- **The privacy test counts every process from the app's folder**
  (`pgrep -f` on its path), so another run of the same build meanwhile (a
  dev session, a manual check) shows up as direct connections. Run nothing
  else from that build during the privacy test.
- **Marionette:** launch with `-marionette -remote-allow-system-access` and use
  `tools/marionette.py` to run JavaScript in the browser window or synthesize
  clicks.
- **Screenshots:** `screencapture -x -o -l <window id>`, with the window id
  from `CGWindowListCopyWindowInfo` (the process's on-screen layer-0 window).
  ruri's bridge can't see this app's window.
- **mach hides its output** when it detects an AI agent (`AI_AGENT`,
  `CLAUDECODE` and others). `./mach build --verbose` shows everything.
- **The user has another Firefox build project (`toji`) on this machine.**
  Only ever kill processes under `/neeko/engine/obj-…` (as `make stop` does).
- **Match a build's programs from the start of the command line, and only
  the browser's.** `make stop` once matched `<checkout>/engine/obj-*/dist/`
  anywhere in a command line, and a running build's clang and rustc jobs
  carry `-I…/engine/obj-release/dist/include`: `make stop` during `make
  release` killed them, failing the release 69 minutes in (Toji found it).
  Packaging also runs tools from `dist/` (xpcshell, in `dist/bin` and in
  the `.app`). So `make stop` and `make wipe` match `^…/dist/<Name>.app/
  Contents/MacOS/firefox` (and its helper `.app`s) or `^…/dist/bin/firefox`
  (and `plugin-container`).
- **The privacy test** (`tools/test_privacy.py`) runs mitmproxy through
  `uvx` (pinned version, nothing installed), trusts its fresh certificate in
  a brand-new profile with NSS's `certutil` (the dev build's, since packaged
  apps don't ship one), and watches `lsof` for connections that skip the
  proxy. With telemetry upload switched back on, some upload went out
  directly, not through the proxy, so that check matters.
- **Quitting normally needs Marionette on macOS.** Firefox doesn't handle
  SIGTERM there, and killing it skips shutdown, when shutdown pings would
  go. The privacy test enables Marionette only to quit and to read
  about:telemetry/about:glean, with `remote.prefs.recommended=false`.
  Chrome-context commands also need `-remote-allow-system-access`.
- **about:glean fills in its upload status late,** and its placeholder says
  "enabled". Wait for its `uploadEnabled: true|false` line before reading
  the status. Its "disabled, but we're lying to the SDK" message means
  upload is actually on.
- **Never run the privacy test through Marionette** (or set
  `remote.prefs.recommended=false`). Marionette applies its own "recommended
  prefs", which turn off telemetry, captive portal checks and more, hiding
  exactly the defaults under test. Reading default values with
  `Services.prefs.getDefaultBranch("")` is fine, since those prefs are user
  values.
- **Firefox Labs and Nimbus:** with studies off, Nimbus still enables its
  recipe loader for Firefox Labs, on a 6-hour timer
  (`app.normandy.run_interval_seconds`) that starts counting at first
  launch. A 4-minute privacy test won't see that request; it goes to the
  kept Remote Settings host and enrolls in nothing unless the user opts in.

## Git

- **Git refuses local-path submodules** unless run with
  `-c protocol.file.allow=always` (`tools/new-browser.ts` does this for local
  Neeko paths).
- **`git describe --tags` picks up feature tags** (`feat-…`). Use
  `--match 'v*'` for release versions.
